## #141 — Không cho tắt thông báo bắt buộc

### Thay đổi
- `UserNotificationSettingService.upsertSetting` — chặn tắt `inAppEnabled`/`pushEnabled` cho
  eventType có `priority="critical"` (không hardcode tên eventType — gate theo priority nên tương
  lai thêm eventType bắt buộc mới tự động được bảo vệ).
- `UserNotificationSettingResponse` thêm field `mandatory` để FE biết khóa switch mà không cần tự
  hardcode danh sách.
- Web Admin (`NotificationSettingsForm.tsx`) và Mobile App (`NotificationSettings.tsx`): khóa
  Switch + hiện icon khóa khi `mandatory=true`.

### A. Test Backend (API thật)
- PUT tắt cả 2 kênh cho `RANDOM_CHECK_SENT` → **422** `MANDATORY_NOTIFICATION`.
- PUT chỉ tắt `inAppEnabled` (giữ push bật) cho `RANDOM_CHECK_SENT` → vẫn **422** (không cho tắt
  1 phần).
- PUT bật cả 2 kênh cho `RANDOM_CHECK_SENT` → **200** (bật thì luôn cho phép).
- PUT tắt `EMPLOYEE_INVITED` (không critical) → **200**, vẫn cho phép tắt bình thường.
- `GET /me/notification-settings` → `RANDOM_CHECK_SENT` và `TENANT_SUSPENDED_OWNER` đều có
  `mandatory:true`; các eventType khác `mandatory:false`.
- `tests/notification/test_notification_settings.sh` — PASS 29/29 (đã thêm Test 9).

### B. Test Frontend
- `tsc --noEmit` sạch cho cả Web Admin và Mobile App sau khi thêm field `mandatory`.
- **CẦN BẠN TEST THỦ CÔNG trên UI thật**: vào trang cài đặt thông báo, xác nhận switch của "Kiểm
  tra ngẫu nhiên" (RANDOM_CHECK_SENT) hiển thị icon khóa và không bấm tắt được — tôi chưa chạy
  Playwright cho phần này trong đợt này (đã test kỹ qua API, phần UI thuần hiển thị/disable rủi ro
  thấp nhưng chưa xác nhận trực quan).

## #144 — Data retention theo tenant

### Thay đổi
- Migration V108: `tenant_settings.data_retention_days` (nullable INT, null = dùng mặc định toàn
  nền tảng).
- `TenantSettingsService`: thêm set/clear qua `PATCH /tenants/{id}/settings`
  (`dataRetentionDays` + `clearDataRetentionDays`), min 7 / max 3650 ngày.
- `DataRetentionJob` viết lại: loop từng tenant active, resolve `effectiveDays` (override riêng
  hoặc mặc định), áp dụng cho:
  - Xóa notification đã đọc: `NotificationRepository#deleteReadNotificationsOlderThan(tenantId, cutoff)`
    (query mới, tenant-scoped).
  - Xóa ảnh selfie: `AiServiceClient#cleanupOldCheckinPhotos(days, tenantId)` (overload mới).
- ai-service (Python): `POST /checkins/cleanup` nhận thêm `tenant_id` optional — quét đúng thư mục
  `checkins/{tenant_id}/` và `liveness_challenges/{tenant_id}/` thay vì toàn bộ.
- `notification_delivery_logs` **giữ nguyên xóa theo config toàn cục** — bảng này không có cột
  tenant_id trực tiếp (chỉ FK `notification_id` nullable, nhiều dòng không join được về tenant nào,
  VD: fallback email cho push-only path) nên không per-tenant hoá được nếu không đổi schema. Ghi rõ
  lý do trong code, không tự ý mở rộng schema thêm trong đợt này.

### A. Test Backend + ai-service (API + DB thật)
- Không có endpoint trigger job thủ công (job chạy cron Chủ nhật 3h sáng) — test từng thành phần
  trực tiếp thay vì đợi cron:
  1. `PATCH` set `dataRetentionDays=45` cho 1 tenant → `GET` phản ánh đúng.
  2. Tạo file ảnh giả 60 ngày tuổi cho tenant target VÀ 1 tenant khác trong `fams-ai` container →
     gọi thẳng `POST /checkins/cleanup?tenant_id=...&older_than_days=45` → **chỉ** xóa đúng file
     tenant target, file tenant kia còn nguyên.
  3. Insert 1 dòng notification đã đọc, 60 ngày tuổi, cho 2 tenant khác nhau → chạy đúng predicate
     SQL mà JPQL `deleteReadNotificationsOlderThan` sinh ra → chỉ xóa đúng dòng tenant target.
- `tests/notification/test_data_retention.sh` (mới) — PASS 7/7.
- `tests/tenant/test_tenant_settings.sh` — thêm Test 9 (set/clear dataRetentionDays, validation
  min/max) — PASS 16/16 toàn bộ file.
- Regression sau khi rebuild `fams-ai`: `test_checkin_face.sh` 5/5 — không lỗi các luồng chấm công
  bằng khuôn mặt hiện có.

### B. Test Frontend
Không có UI riêng cho `dataRetentionDays` trong đợt này (chưa có yêu cầu cụ thể thêm field này vào
màn Cài đặt tenant trên Web Admin) — chỉ dừng ở API. **Ghi nhận follow-up**: nếu muốn tenant admin
tự cấu hình qua UI thay vì chỉ qua API/Postman, cần thêm 1 input số vào trang Company Settings.

## #146 — Audit khi bị từ chối quyền

### Thay đổi
- `GlobalExceptionHandler.handleAccessDenied` — thêm ghi audit `ACCESS_DENIED` (best-effort, theo
  khuôn mẫu `PLAN_LIMIT_DENIED`) mỗi khi bất kỳ `@PreAuthorize`/service-layer permission check nào
  từ chối request (116 chỗ dùng `@PreAuthorize` trong toàn hệ thống đều đi qua handler này).
  `tenantId` được suy ra best-effort từ path request (`/tenants/{uuid}/...`), null nếu endpoint
  không tenant-scoped.

### A. Test Backend (API + DB thật)
- Tạo 1 tenant + 1 user không có role nào trên tenant đó → PATCH profile tenant → **403** đúng.
- Query `audit_logs` → có đúng 1 dòng `action='ACCESS_DENIED'`, `tenant_id` đúng, `entity_type=
  'AccessControl'`, `new_value` chứa path + lý do (`"Only this tenant's owner may update its
  profile"`).
- `tests/security/test_permission_guards.sh` — thêm phần tự-setup không cần env var, PASS 16/16.

### B. Test Frontend
Không có UI riêng cho sự kiện bị từ chối quyền (người dùng thấy toast lỗi 403 chung) — không nằm
trong phạm vi AC yêu cầu vá thêm.
