## #1 — Bắt buộc xác thực OTP khi đăng ký bằng số điện thoại

### Vấn đề gốc
`RegisterService.register()` (phone-only path) tạo `users` row với `is_active=true`, `email_verified=true` (mặc định coi phone-only là "đã verified" — sai, comment cũ trong code còn ghi nhầm "verified via OTP at login" dù chưa hề có bước OTP nào) và **cấp JWT token thật ngay lập tức** — người dùng coi như đăng nhập thành công chỉ bằng cách gửi `{phone, password, displayName}`, không hề có bước xác thực số điện thoại là có thật.

Khảo sát cho thấy 2 hạ tầng OTP đã tồn tại:
- `OtpService` (Redis + `SmsService` tự viết) — **dead code**, 0 nơi gọi tới, `SmsService` chỉ có 1 implementation là `ConsoleSmsService` (dev stub, chỉ log ra console, không gửi SMS thật).
- `FirebasePhoneLoginService` — dùng cho **đăng nhập** SĐT: verify một Firebase ID Token (client tự hoàn tất OTP với Firebase, backend chỉ verify token), yêu cầu user đã tồn tại sẵn.

Quyết định: đăng ký SĐT nên tái sử dụng đúng cơ chế Firebase đã có (đã production-ready, có SMS thật qua Firebase), **không hồi sinh** `OtpService` chết vì nó cần viết thêm SMS provider thật từ đầu mà không có lý do — đây chính là ý "làm như các hệ thống thông thường hay làm" mà bạn xác nhận.

### Thay đổi
- **Migration** `V57__add_phone_verified_to_users.sql`: thêm `users.phone_verified BOOLEAN NOT NULL DEFAULT FALSE`.
- **`User.java`**: thêm field `phoneVerified`.
- **`FirebasePhoneTokenVerifier`** (mới, `modules/auth/service/`): tách logic verify Firebase ID Token (trước đây nằm private trong `FirebasePhoneLoginService`) thành 1 component `@Component` dùng chung — tránh trùng lặp code Firebase Admin SDK giữa luồng login và luồng register.
- **`FirebasePhoneLoginService`**: refactor để gọi `FirebasePhoneTokenVerifier` thay vì tự verify — hành vi giữ nguyên 100% (đã test lại `tests/auth/test_otp_login.sh` và gọi trực tiếp `/otp/verify`, cùng response 503 khi Firebase chưa cấu hình như trước khi refactor).
- **`RegisterRequest`**: thêm field `firebaseIdToken` (optional ở tầng DTO, bắt buộc có điều kiện ở tầng service).
- **`RegisterService.register()`**: với nhánh phone-only (`phone != null && email == null`) — nếu thiếu `firebaseIdToken` → `PhoneNotVerifiedException` (400, `PHONE_NOT_VERIFIED`); nếu có, verify qua `FirebasePhoneTokenVerifier`, so khớp số điện thoại trong token với số đã submit (chuẩn hoá thêm `+` nếu thiếu) — không khớp cũng ném `PhoneNotVerifiedException`; khớp → tạo user với `phoneVerified=true`, cấp token như cũ.
- **`PhoneNotVerifiedException`** (mới) + `GlobalExceptionHandler.handlePhoneNotVerified` → HTTP 400, error code `PHONE_NOT_VERIFIED`.
- **Swagger**: cập nhật `@Operation`/`@ApiResponses` của `POST /auth/register` để khai đúng 400 (PHONE_NOT_VERIFIED)/401 (INVALID_OTP)/503 (Firebase chưa cấu hình).

### Test
- `tests/auth/test_register.sh`: Test 4 đổi từ "phone-only → 201 + token" (hành vi cũ, sai) sang "phone-only không kèm `firebaseIdToken` → 400 PHONE_NOT_VERIFIED"; thêm Test 4b (token giả → 401, hoặc 503 nếu môi trường chưa cấu hình Firebase thật — môi trường dev hiện tại không có `FCM_SERVICE_ACCOUNT_JSON` thật nên sẽ thấy 503, đây **không phải lỗi**, là giới hạn môi trường giống `test_otp_login.sh` từ trước); Test 5 (duplicate phone) sửa lại để tự seed một tài khoản qua SQL trực tiếp trước khi test (vì giờ không thể tạo tài khoản trùng qua API mà không có Firebase token thật).
- `tests/auth/test_register_phone_otp.sh` (mới): test thủ công đi qua Firebase thật (giống mẫu `test_otp_login.sh`) — dùng Firebase test phone number để không tốn quota SMS thật, xác nhận toàn bộ luồng hoạt động đúng đầu cuối.
- Đã chạy `test_register.sh` + `test_login.sh` + `test_otp_login.sh` trên môi trường dev hiện tại: 11/11 pass (1 test INFO-skip do môi trường chưa có Firebase thật), không có regression.

### Cách tự test trên Swagger / thực tế
1. Không có Firebase project thật đang cấu hình trong `.env` của máy bạn (`FCM_SERVICE_ACCOUNT_JSON` hiện chỉ là placeholder) — để test đầu-cuối thật (nhận SMS thật), cần cấu hình Firebase project + Web API Key, sau đó chạy `FIREBASE_API_KEY=... bash tests/auth/test_register_phone_otp.sh`.
2. Không có Firebase, vẫn test được phần chặn: `POST /api/v1/auth/register` với `{"phone":"+84912345678","password":"Test@1234","displayName":"Test"}` (không kèm `firebaseIdToken`) → phải nhận **400 PHONE_NOT_VERIFIED**. Đây là hành vi có thể tự kiểm chứng ngay trên Swagger UI mà không cần Firebase thật.
3. Kiểm tra DB: `SELECT phone, phone_verified FROM users WHERE phone IS NOT NULL;` — các tài khoản đăng ký từ nay trở đi phải có `phone_verified=true` (nếu tạo thành công) thay vì luôn `false`/không có cột.

## #2 — Gửi lại mã xác thực khi đăng ký email

### Vấn đề gốc
`POST /api/v1/auth/verify-email?token=...` (xác thực) đã có sẵn, nhưng không có cách nào để lấy lại link nếu email bị mất/hết hạn (token TTL mặc định 24h) ngoài việc đăng ký lại từ đầu (mà đăng ký lại sẽ bị chặn bởi lỗi email đã tồn tại).

### Thay đổi
- **`ResendVerificationRequest`** (mới): `{ email }`.
- **`EmailVerificationService.resendVerification(email)`** (mới) — copy đúng khuôn mẫu bảo mật của `PasswordResetService.forgotPassword()` đã có sẵn trong cùng module:
  - Rate limit theo email: Redis key `email:verify:resend:rate:{email}`, mặc định tối đa 3 lần/10 phút (`app.email.resend-rate-limit-max`, mặc định 3) — vượt quá thì âm thầm bỏ qua (không trả lỗi, không lộ rate limit).
  - Email không tồn tại, hoặc tồn tại nhưng **đã verified** → âm thầm bỏ qua (log debug, không lộ thông tin tài khoản có tồn tại hay không, đúng nguyên tắc chống dò email của `forgot-password`).
  - Còn lại → sinh token mới (`generateToken`, không thu hồi token cũ — token cũ vẫn còn hiệu lực tới khi hết TTL hoặc được dùng, giống hệt cách `forgotPassword` xử lý token cũ) và gửi lại email qua `EmailService.sendVerificationEmail` (dùng chung, không viết mới).
- **`AuthController`**: thêm `POST /auth/resend-verification`, luôn trả 200 với message chung chung, không phân biệt các trường hợp phía trên.
- **`SecurityConfig`**: thêm `POST /api/v1/auth/resend-verification` vào danh sách `permitAll()` — endpoint public như các endpoint đăng ký/quên-mật-khẩu khác (bị bỏ sót lúc đầu, gây lỗi 401 khi test — đã tự phát hiện và sửa ngay trong lúc test tay).

### Test
- `tests/auth/test_resend_verification.sh` (mới): resend cho tài khoản chưa verify → 200 (xác nhận qua log server thực sự có gửi lại mail); resend cho email không tồn tại → 200 (không lộ); resend cho tài khoản đã verify (`admin@fams.com`) → 200 (no-op); email sai định dạng → 400; rate limit — gọi 4 lần, xác nhận qua Redis (`GET email:verify:resend:rate:{email}` phải ≥ 4) rằng lần thứ 4 đã bị chặn gửi thật (kiểm chứng thêm bằng tay qua `docker logs fams-api` thấy dòng `WARN ... rate limit hit` đúng ở lần gọi thứ 4, còn 3 lần đầu đều có dòng `EmailService — Verification email sent`).
- Chạy lại `test_register.sh`, `test_login.sh`, `test_google_login.sh` — không có regression (tất cả pass), xác nhận việc thêm dependency mới vào `EmailVerificationService` (constructor injection `EmailService`, `baseUrl`, rate-limit config) không ảnh hưởng `RegisterService` (nơi duy nhất khác đang dùng `EmailVerificationService`).

## #3 — Người dùng thuộc nhiều công ty + gói mặc định khi tự tạo công ty

### Vấn đề gốc
`POST /api/v1/tenants` có `@PreAuthorize("hasRole('PLATFORM_ADMIN')")` — chỉ Platform Admin mới tạo được công ty (`TenantController.java`). `TenantService.createTenant()` cũng **không hề insert `user_roles`** cho người tạo (chỉ set `tenants.owner_id`, một cột FK đơn thuần không cấp quyền gì) — nên kể cả nếu bỏ chặn ở controller, một user thường gọi thành công vẫn sẽ không có quyền gì trên công ty vừa tạo (không phải TENANT_ADMIN, không thấy công ty đó ở đâu cả). Không có ràng buộc DB/service nào chặn 1 user thuộc nhiều tenant (`user_roles` unique constraint là `(user_id, role_id, tenant_id)`, không phải theo `user_id` riêng) — phần "đa công ty" vốn đã khả thi về mặt dữ liệu, chỉ là API tạo tenant chưa mở cho user thường.

Plan: hệ thống có 4 plan (`trial`, `basic`, `pro`, `enterprise`), **không có plan nào tên "Free"**. `trial` giá 0đ, `sort_order` thấp nhất, và `createTenant()` từ trước đã tự động gán plan có `sort_order` nhỏ nhất cho tenant mới — tức cơ chế "mặc định nhận gói miễn phí" **đã hoạt động sẵn**, chỉ khác tên gọi (Trial thay vì Free).

### Thay đổi
- **`TenantController.createTenant`**: bỏ `@PreAuthorize("hasRole('PLATFORM_ADMIN')")` — endpoint giờ chỉ cần đăng nhập (JWT hợp lệ), không cần role cụ thể. Cập nhật Swagger mô tả rõ hành vi mới, bỏ mô tả 403 sai (không còn đúng).
- **`TenantService.createTenant(request, createdByUserId, createdByPlatformAdmin)`**: thêm tham số `createdByPlatformAdmin`. Sau khi tạo tenant + subscription như cũ, nếu người tạo **không phải** Platform Admin → tự động insert `user_roles` gán role `TENANT_ADMIN` (tra bằng `roleRepository.findByNameAndTenantIdIsNull("TENANT_ADMIN")`, role hệ thống có sẵn) cho `tenantId` vừa tạo, `assignedBy` = chính người đó. Nếu người tạo LÀ Platform Admin → giữ nguyên hành vi cũ (không tự gán quyền gì, vì admin thường tạo hộ khách hàng chứ không phải tự tham gia công ty).
- Không đổi gì về plan mặc định — cơ chế gán `trial` (sort_order thấp nhất) giữ nguyên như cũ, chỉ xác nhận lại nó vẫn chạy đúng cho luồng self-serve mới.

### Test
- `tests/tenant/test_create_tenant.sh`: Test 7 đổi từ "user thường bị 403" (hành vi cũ) sang "user thường tạo được tenant (201) và tự động có role TENANT_ADMIN" (kiểm chứng qua query `user_roles JOIN roles`); thêm Test 8 (cùng 1 user tạo tenant thứ 2 — xác nhận đa công ty hoạt động thật qua API, không chỉ ở tầng DB); thêm Test 9 (Platform Admin tạo tenant thì **không** tự nhận role trong đó — bảo vệ hành vi cũ không bị đổi ý ngoài ý muốn). Cả 9/9 test pass.
- Xác nhận qua SQL: 2 tenant tự-tạo trong test đều có `tenant_subscriptions.status = TRIAL` với `plans.name = 'trial'` — đúng cơ chế gán mặc định.

### ⚠️ Cần bạn xác nhận: Trial hay Free thật sự riêng biệt?
Mình dùng `trial` (đã có sẵn, giá 0đ) làm gói mặc định thay vì tạo thêm 1 plan "Free" mới, vì không rõ nghiệp vụ có muốn 2 khái niệm khác nhau (Trial có hạn dùng thử vs Free dùng vĩnh viễn không giới hạn thời gian) hay chỉ đơn giản gọi tên khác nhau cho cùng 1 thứ. Nếu bạn muốn tách riêng, báo lại — đây là quyết định về mô hình gói dịch vụ, không phải lỗi kỹ thuật nên mình không tự ý thêm plan mới.

### Cách tự test trên Swagger
1. Đăng nhập bằng 1 tài khoản thường (không phải platform admin) → gọi `POST /api/v1/tenants` với `{"name":"Công ty Test","slug":"cong-ty-test-1"}` → phải nhận **201**.
2. Query DB: `SELECT ur.*, r.name FROM user_roles ur JOIN roles r ON r.id=ur.role_id WHERE ur.tenant_id='<id vừa tạo>';` → phải thấy đúng 1 dòng `TENANT_ADMIN` gán cho user vừa gọi.
3. Tạo tiếp tenant thứ 2 với cùng token đó (`slug` khác) → vẫn 201, xác nhận 1 người có thể sở hữu nhiều công ty.
4. `SELECT p.name FROM tenant_subscriptions ts JOIN plans p ON p.id=ts.plan_id WHERE ts.tenant_id='<id>';` → phải là `trial`.

## #4 — Bổ sung trường hồ sơ người dùng

### Vấn đề gốc
`UpdateProfileRequest`/`UserProfileResponse` chỉ có `displayName, phone, avatarUrl`. `avatarUrl` chỉ là 1 chuỗi URL — không có endpoint nào nhận file ảnh thật, người dùng phải tự host ảnh ở đâu đó rồi dán link vào, không đúng ý "đẩy ảnh từ máy cá nhân". Không có nơi nào trong cả backend từng có tính năng nhận file upload lưu trữ lâu dài (chỉ có nơi forward MultipartFile thẳng sang AI service ngoài cho Face ID, không lưu file).

### Thay đổi
- **Migration `V58__add_profile_fields_to_users.sql`**: thêm `date_of_birth DATE, hometown VARCHAR(255), gender VARCHAR(20), address VARCHAR(500)` vào `users`.
- **`UpdateProfileRequest`/`UserProfileResponse`/`User` entity**: thêm 4 trường tương ứng. `dateOfBirth` validate `@Past` (không cho ngày sinh trong tương lai). `hometown/gender/address` theo đúng convention đã có của `displayName` (chỉ cập nhật nếu có giá trị, không có cách "xóa trắng" qua chuỗi rỗng — nếu cần xóa, dùng `avatarUrl` làm mẫu vốn đã hỗ trợ chuỗi rỗng để clear).
- **`AvatarStorageService`** (viết lại theo yêu cầu của bạn — chuyển từ local disk sang S3-compatible object storage, dùng `software.amazon.awssdk:s3`): validate content-type (jpeg/png/webp) + Spring multipart giới hạn 5MB (`spring.servlet.multipart.max-file-size`); upload qua `S3Client.putObject`. Cùng 1 đoạn code chạy được với cả MinIO (dev) lẫn AWS S3 thật (production) — chỉ khác cấu hình: có `app.s3.endpoint` (VD `http://fams-minio:9000`) → dùng path-style addressing + tự tạo bucket nếu chưa có (tiện cho dev, không đụng tới production vì production luôn tạo bucket sẵn qua hạ tầng riêng); để trống `app.s3.endpoint` → SDK tự nói chuyện thẳng với AWS S3 thật bằng access key/secret key cấu hình.
  - **Bug thật tự phát hiện lúc test**: ban đầu định dùng URL công khai qua `app.base-url` (biến trỏ origin Web Frontend `http://localhost:3000` để link email click được, xem `fams-front-web-project/next.config.ts`) — nhưng Next.js không proxy đường dẫn ảnh, sẽ 404. Đã tách riêng `app.s3.public-url` chỉ dùng cho URL ảnh.
  - **Bug thật thứ 2 tự phát hiện lúc test**: set `ObjectCannedACL.PUBLIC_READ` trên từng object không có tác dụng — MinIO không tự động cho phép đọc public chỉ vì ACL đó, và nhiều tài khoản AWS S3 thật còn tắt hẳn ACL (chính sách "Bucket owner enforced" mặc định của AWS hiện nay). Đã sửa đúng theo cách các hệ thống thực tế hay làm: dùng **bucket policy** (`s3:GetObject` public cho prefix `avatars/*`) thay vì ACL từng object — set 1 lần khi bucket được tạo (dev) hoặc production tự cấu hình sẵn.
- **`SecurityConfig`**: bỏ `GET /uploads/**` (không còn serve file local nữa, ảnh giờ ở object storage riêng, phục vụ trực tiếp từ đó).
- **`docker-compose.dev.yml`**: thêm service `minio` (image `minio/minio`, có healthcheck, volume `minio_data` riêng) — chỉ ở dev override, production không cần vì dùng AWS S3 thật.
- Loại bỏ hẳn `WebConfig`/local-disk static serving đã viết ban đầu (không cần nữa sau khi chuyển sang object storage).

### Test
- `tests/auth/test_profile_fields_and_avatar.sh` (mới, 6/6 pass): cập nhật đủ 4 trường mới + đọc lại đúng; ngày sinh tương lai bị từ chối; upload PNG hợp lệ → 200 + file thật sự truy cập được qua URL trả về; upload lại → file cũ 404 (xác nhận cleanup hoạt động), file mới 200; upload file không phải ảnh → 400; không có token → 401.

### ⚠️ Cần bạn xác nhận: lưu trữ ảnh ở đâu lâu dài?

Cách này chạy tốt cho 1 instance backend hiện tại, nhưng nếu sau này scale nhiều instance hoặc muốn dùng CDN thật, sẽ cần đổi sang cloud storage — thiết kế hiện tại (URL string, đổi 1 class `AvatarStorageService`) đã tính trước cho việc này nên không khó đổi sau. Báo lại nếu bạn muốn làm cloud storage ngay bây giờ thay vì local disk.

## #6 — Quản lý thiết bị/phiên đăng nhập

### Vấn đề gốc
Không phải "lỗi" mà là tính năng chưa tồn tại: không có `GET /auth/sessions` nào cả; `LogoutService.logout()` chỉ nhận đúng raw refresh token của chính thiết bị gọi (không có tham số ID để chỉ định thiết bị khác); `logoutAll()` luôn thu hồi cả phiên hiện tại, không có tuỳ chọn giữ lại; `refresh_tokens` không có cột nào để hiển thị (không `last_used_at`, không user-agent/IP).

## #5 — Sửa lỗi bảo mật 2 lớp (2FA)

### Vấn đề gốc (khảo sát bằng agent đọc kỹ toàn bộ luồng TOTP)
Mô tả ban đầu của bạn chỉ nói chung chung "lỗi bảo mật 2 lớp" — sau khi đọc kỹ `TotpService`, `LoginTotpService`, migration, và test hiện có, xác định được 3 vấn đề thật, xếp theo mức độ nghiêm trọng:

1. **[Nghiêm trọng] `POST /totp/disable` không xác thực lại**: method cũ chỉ nhận `UUID userId` từ JWT, set `totpEnabled=false` ngay — không mật khẩu, không mã TOTP. `tests/auth/test_login_totp.sh` cũ còn coi việc gọi disable chỉ bằng Bearer token là hành vi "cleanup" bình thường, xác nhận đây không phải side-effect ai đó cố ý, mà là thiết kế thiếu sót thật.
2. **[Cao] `users.totp_secret` lưu plaintext**: `V16__add_totp_to_users.sql` khai báo `VARCHAR(255)` thường, `TotpService.enableTotp()` cũ set thẳng secret Base32 vào đó không qua bất kỳ mã hóa nào.
3. **[Trung bình] Không có backup codes**: grep toàn bộ codebase không thấy bảng/field nào liên quan "backup code". Vì luồng gỡ 2FA (`disable`) đòi hỏi phải đăng nhập được, mà TOTP-gated login lại đòi hỏi có 2FA hoạt động → mất thiết bị = khóa tài khoản vĩnh viễn, không có lối thoát.

### Thay đổi
- **`TotpSecretCipher`** (mới): AES-256-GCM, key suy ra qua SHA-256 từ passphrase cấu hình `app.totp.encryption-key` (env `TOTP_ENCRYPTION_KEY`, bắt buộc, đã thêm giá trị thật vào `.env` bằng `openssl rand -hex 32`, thêm placeholder vào `.env.example`). IV ngẫu nhiên mỗi lần mã hóa, IV+ciphertext gộp base64 khi lưu.
- **Migration `V59__create_totp_backup_codes.sql`** + entity/repo `TotpBackupCode`: bảng riêng, mỗi code là 1 dòng, hash bằng BCrypt (giống mật khẩu — one-way, không cần giải mã lại vì so khớp là đủ), có `used_at` để đánh dấu đã dùng.
- **`TotpService.enableTotp()`**: mã hóa secret trước khi lưu (`secretCipher.encrypt`); sinh 8 backup code ngẫu nhiên (bảng chữ bỏ ký tự dễ nhầm `0/O/1/I`), hash từng cái, lưu, xóa hết code cũ trước (idempotent nếu bật lại); trả về `TotpEnableResponse{backupCodes}` — đây là **lần duy nhất** client thấy plaintext codes.
- **`TotpService.disableTotp(userId, request)`**: bắt buộc đúng 1 trong `password`/`code`/`backupCode` khớp mới cho tắt; kiểm tra `isTotpEnabled()` trước, chưa bật thì 400 (`IllegalStateException`) thay vì set giá trị vô nghĩa; tắt xong xóa luôn toàn bộ backup code liên quan.
- **`LoginTotpService`**: chấp nhận `backupCode` thay `code` (dùng `TotpService.consumeBackupCode` — single-use, đánh dấu `used_at` ngay khi khớp).
- **`TotpService.verifyStoredCode(user, code)`** (mới): điểm truy cập chung để giải mã + verify, tránh rải logic giải mã ở nhiều nơi.
- **Swagger**: cập nhật mô tả `/totp/verify`, `/totp/disable`, `/login/totp` phản ánh đúng hành vi mới; sửa luôn 1 lỗi tài liệu có sẵn (disable từng khai 409 "chưa bật 2FA" nhưng code chưa từng thực sự trả 409 — nay đúng 400, khớp với cách `IllegalStateException` được xử lý ở `GlobalExceptionHandler`).

### Sự cố phát sinh trong lúc test (đã xử lý)
Khi test thủ công luồng mới, phát hiện `admin@fams.com` đang bị **kẹt ở trạng thái `totp_enabled=true`** — dư âm từ 1 lần chạy `tests/run_all.sh` trước đó bị gián đoạn giữa chừng do mình restart container (để nạp code #4/#5) trong lúc suite đang chạy. Vì bước cleanup cũ của `test_login_totp.sh` (chỉ gọi disable bằng Bearer token, không kèm mật khẩu) giờ không còn hợp lệ với yêu cầu xác thực lại mới, tài khoản admin bị treo 2FA vĩnh viễn sau lần chạy đó — ảnh hưởng dây chuyền tới **mọi** test khác đăng nhập bằng admin (chúng mong đợi nhận token ngay, nhưng giờ sẽ nhận `totpRequired:true`). Đã: (a) reset trực tiếp qua SQL để đưa admin về trạng thái sạch, (b) sửa `test_login_totp.sh` để bước cleanup gửi đúng mật khẩu admin, tự dọn dẹp đúng cách ở mọi lần chạy sau này.
